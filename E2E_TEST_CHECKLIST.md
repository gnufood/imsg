# Live end-to-end test checklist

Written 2026-07-23. Companion to `GUI_NEXT.md` §1 ("Live end-to-end test — not yet run — the
one unmet validation"). Everything below is unit/integration tested (real sockets, real
SQLite, hermetic keyring bypass) but never exercised as a running app against a real phone.

This list was built by diffing local `main` against `origin/main` (66 commits ahead, 0
behind — nothing pushed since `686b6c0`) rather than assuming the gap was GUI-only. A
significant share of what's untested is backend/CLI: a new `imsg-broker-client` crate, a CLI
lib/bin split with a rewritten dispatch/broker path, live (non-cached) PBAP contact ops routed
through the broker, RFCOMM `BT_SECURITY` support (`setsockopt`, explicitly noted in-tree as
untested against hardware), real Bluetooth SDP discovery, and a config-layer rewrite
(`toml_edit`-typed writes, `SecurityLevel`). See `GUI_NEXT.md` §1 for setup/run/verify
procedure (config stashing, log locations, screens viewable without a phone).

**Findings from Phase 1 (no daemon, no sync):**
1. `folders` errors instantly on every call — needs separate root-cause pass.
2. `list --from` does no phone-number normalization: `--from 4084559969` (bare, no country code) silently returns `(no messages)` instead of matching or erroring; `--from +14084559969` works correctly. Likely wants normalization or a clearer no-match distinction from a malformed-filter case.
3. `get <handle>` on a message just sent via `send` shows `From:` blank and `Folder: telecom/msg/inbox` — an outbound message reporting as inbox with no sender looks wrong, though semantics of `From` for self-sent messages need confirming against intended design.
4. `get <handle>` does not reflect post-`delete` state: after `imsg delete <handle>` succeeded and the message was confirmed moved into the `deleted` folder (via `imsg list deleted`), `imsg get` on that same handle still showed the original `Folder: telecom/msg/inbox` and `Status: unread` — stale read, not reflecting the actual current folder/status.

**Findings from Phase 2 (no daemon, sync'd):**

5. **`imsg sync` output is misleading, and `threads`/`list` print a false "never synced" footer despite reading real synced data correctly.** `imsg sync` only ever printed a contacts count ("sync complete; 194 contacts synced", then "0 contacts synced" on a second run) with zero indication of message-sync activity, which looked at first like `sync` wasn't backfilling messages at all. Opened the local SQLCipher store directly (`sqlcipher` CLI, key retrieved from the OS Secret Service under service=`imsg`/account=`database-encryption-key` — see `imsg-keyring` crate, `SERVICE`/`ACCOUNT` consts in `crates/imsg-keyring/src/lib.rs`) and confirmed: `messages` table has 10 real rows, `folder_cursors` shows all four folders (`inbox`/`sent`/`deleted`/`outbox`) with `sync_status: complete`, and the row content/order exactly matches what `imsg threads`/`imsg list` display. **So sync genuinely works** — the bug is purely in the CLI's status footer, which prints `(never synced — run 'imsg sync' to populate the store)` unconditionally instead of checking actual sync state (e.g. `folder_cursors.sync_status` or `meta.sync_enabled`, both of which correctly show synced/true in the DB).
6. **Data-loss/mismatch between live and synced views.** Phase 1's live `imsg threads` showed a 5th thread, `4084765919` (1 message, no `+1` prefix), that is completely absent from the synced store — neither in `messages` nor reflected in synced `threads` output. Needs investigation: could be a phone-number-format edge case in the sync ingest path (numbers without a leading `+1` being dropped or mis-keyed), separate from finding 2's CLI-arg-normalization issue but possibly related.
7. **Re-tested via CLI: handle itself is stable; real cause is `send` misfiling into the wrong folder, which then makes `delete`'s default `--folder inbox` target the wrong place.** Sent a fresh throwaway test message (`imsg send +14084559969 "...handle-check..."`) and immediately checked `imsg list outbox -l`, `imsg list sent -l`, `imsg list inbox -l --from +14084559969`. Result: the handle `imsg send` returned (`C2A3F32A1F13411`) matches **exactly** in `imsg list sent -l` — handle is stable, not reassigned between outbox/sent as originally hypothesized. This directly contradicts the earlier hypothesis in this entry (now struck through) and rules it out. However, this new message correctly landed in `sent`, whereas the original Phase-1 test message was sitting in `inbox` (confirmed via the direct DB read in finding 5's investigation). So the real anomaly is that the **Phase-1 send was misfiled into `inbox` instead of `sent`** — and since `imsg delete` defaults to `--folder inbox` when `--folder` is omitted, deleting a message that's actually resting in `sent` while asking for `inbox` would explain the original apparent no-op (issue #4).
   - **CONFIRMED (2026-07-24):** `imsg delete 7B093DFC01064E4` (the original Phase-1 test message handle, no `--folder` flag, so defaulting to `inbox`) succeeded this time — `deleted 7B093DFC01064E4`. This matches the theory: the message really was resting in `inbox` (not `sent`), so the default-folder delete correctly targeted it. **Still open:** why did this message land in `inbox` in the first place when a separately-sent message (`C2A3F32A1F13411`) correctly landed in `sent`? Two `send` calls, same recipient, inconsistent filing folder — root cause not identified, needs a controlled repro (multiple sends in a row, compare filed folder each time).
   - Earlier retries of `imsg delete C2A3F32A1F13411 --folder sent` and later `imsg delete C2A3F32A1F13411` (no folder) both failed with `Error: device unreachable — bring the phone close and check Bluetooth`, while `imsg send`/`imsg list` succeeded moments before and after. Suggests `delete` specifically may be hitting connection issues that `send`/`list`/`threads` don't — could be a distinct RFCOMM/MAP-session problem for the delete op path, not just generic Bluetooth flakiness. Not yet root-caused; only anecdotal from this session's ordering of commands.

8. **CONFIRMED real bug, not resolved by finding 7 — self-sent message missing from `inbox` entirely.** Sent `imsg send 4084559969 'test'` (handle `5415C2A2E386484`) — **`4084559969` is the user's own number**, i.e. this is a self-send. `imsg list sent -l` correctly shows it filed in `sent`. But unlike a normal SMS-to-self (which should arrive back as a received message too, since the phone is messaging itself), it **never appears in `inbox`** across repeated checks and elapsed time. This is a real gap, not just "wrong folder checked" — a self-sent message should reasonably show up in both `sent` and `inbox` (or the CLI/store needs to explicitly document that self-sends are sent-only, if that's intended MAP/carrier behavior — not yet known which).
9. **`[sent?]` status marker — the literal question mark suggests the code itself is uncertain about outgoing status, not just display polish.** Both `5415C2A2E386484` and `C2A3F32A1F13411` show `[sent?]` in `imsg list sent -l` output. This isn't a normal terse status label — the trailing `?` reads as the implementation being unsure whether the message actually reached `sent`/delivered state, likely tied to the `outgoing_status` column seen in the local DB schema (finding 5's investigation: `messages` table has an `outgoing_status` column). Needs clarification: is `[sent?]` a deliberate "unconfirmed" state the CLI surfaces intentionally, or a placeholder/bug where a proper status was never wired up?
10. **`(never synced...)` footer bug (finding 5) also reproduces here** — `imsg list sent -l` still prints `(never synced — run 'imsg sync' to populate the store)` despite this being the same already-synced store confirmed working in finding 5. Same root cause, just noting a second reproduction in a different folder view.

**Findings from Phase 3 (daemon, no sync):**

11. **UPDATE to finding 8 — self-sent messages DO eventually land in `inbox`, just not immediately, and under a NEW handle different from the one `send` returned.** Under Phase 3 (daemon started fresh, no sync), `imsg list -l` (default inbox, live from device) now shows both Phase-2 self-sent test messages present in `inbox`: `D6588BB7B23E462` ("test") and `9616AE14328D4EE` ("imsg e2e test - handle-check..."). Neither handle matches what `send` originally returned for these messages (`5415C2A2E386484` and `C2A3F32A1F13411` respectively) — confirmed via `imsg list sent -l`, which now shows `(no messages)`, i.e. they've moved out of `sent` entirely and into `inbox` under fresh handles. So finding 8 is resolved as "not a bug, just eventual/delayed delivery" — but this surfaces a **new, more significant issue**: a message handle is not stable once a self-sent message completes its round trip from `sent` to `inbox`; anything that cached/referenced the original `send`-returned handle (e.g. a GUI showing "message sent" tied to that handle, or a future `delete`/`get` call using it) would silently be referencing a handle that no longer resolves to the message's current location, without any indication the handle changed.
12. **Not an `imsg` bug — Apple/iOS doesn't honor MAP delete-status requests.** `7B093DFC01064E4` was confirmed deleted in Phase 2 (`imsg delete 7B093DFC01064E4` succeeded, absent from subsequent `list` output within that phase/session) but reappeared unchanged in `inbox` under Phase 3 (fresh daemon, no sync). **User-confirmed root cause: this is known iOS behavior — Apple's MAP server implementation does not durably persist/respect delete-status flags set by an accessory.** `imsg`'s `set_message_status_deleted` call is working as intended (finding 7 already confirmed the CLI correctly applies the delete request when given the right folder); the phone simply doesn't keep it applied. Not actionable on the `imsg` side beyond documenting the limitation — e.g. the GUI's delete-conversation flow (checklist item under "GUI — Messages screen") should probably not present delete as a guaranteed-permanent action against an iPhone, since the device itself can silently un-delete.

**Findings from Phase 4 (daemon, sync'd):**

13. **CONFIRMED real bug — `imsg delete` hard-fails with a local SQLite `FOREIGN KEY constraint failed` when the target message isn't present in the local synced store, even though it exists on the device.** Sent a fresh message under Phase 4 (`imsg send +14084559969 "...phase4 daemon-sync..."`, handle `47BD9811294F46B`). `imsg get 47BD9811294F46B` correctly found it on the device (`Folder: telecom/msg/sent`, body correct). But `imsg list sent -l` does **not** show this message at all (only an older Phase-3 leftover message) — reproduced on retry, not a timing fluke. `imsg list outbox -l` is also empty. Then `imsg delete 47BD9811294F46B --folder sent` fails outright: `Error: operation failed: connection error: Error("FOREIGN KEY constraint failed")` — a raw SQLite error surfaced to the user with `-vv` adding no further context (no table/column named, no indication what local row was expected to exist). Root cause (not confirmed further per staying within CLI-observable behavior): `delete` likely tries to update/insert a row in the local synced store keyed to the message, but since `sync` never actually pulled this particular message into the local `sent` table (matching the `list sent` gap), the FK reference has nothing to point at, and the write fails instead of falling back to a live-only delete path. **This is worse than a cosmetic bug** — a delete request that fails with a raw DB error, on a message that verifiably exists (per `get`), leaves the user with no clear signal of what happened or how to recover (was it deleted or not? does retrying help? should they re-sync first?).

**Deferred check — RUN (2026-07-24).** `imsg daemon stop` immediately followed by a plain `imsg list`, no delay, to check for a lifecycle race between daemon-stop and the CLI's dispatch-path fallback to direct/no-daemon mode.

14. **Confirmed real race, but benign in practice — `imsg daemon stop` is asynchronous, and `imsg daemon status` can report stale `connected` state immediately after.** Sequence: `imsg daemon stop` printed `daemon for EC:0D:51:C7:58:64: stopping` (not a final "stopped" state) → immediately ran `imsg list`, which succeeded cleanly with fresh live data and the correct `(live from device)` footer, no error or hang → immediately ran `imsg daemon status`, which reported **`connected`** (stale — the daemon was actively shutting down, not connected) → waited ~3s and re-checked: `not running`, confirmed by both `imsg daemon status` and an empty `ps aux` grep. **So the actual risk is narrower than originally feared**: `list`/other commands handle the mid-stop window gracefully by falling back to a direct connection rather than erroring or hanging against the dying daemon. The real gap is purely in `daemon status` reporting: for some window after `stop` is issued, `status` can claim `connected` when the daemon is in fact already tearing down. Low severity on its own, but worth fixing since anything polling `daemon status` (including the GUI's `StatusDot`, per the checklist's GUI-Settings section) could show incorrect state for a few seconds during shutdown.

**Findings from `imsg contacts` testing (2026-07-24, daemon running, sync active from Phase 4):**

15. **`imsg contacts --list` returns inconsistent formats/data across consecutive calls.** First call (`imsg contacts --list --limit 10`) returned clean, real data: UIDs like `41.vcf`/`42.vcf`, names like `jason`/`ashton`/`sasha🐺`, footer `(live from device)`. After running `imsg contacts --sync` (which reported `synced 0 contacts` — see finding 16), a second `imsg contacts --list --limit 5` returned **completely different-looking data**: short hex-like UIDs (`b8`, `9f`, `d1`), garbled/wrong "names" (`20 lines`, `6 lines` — these look like leftover vCard line-count artifacts, not names), and the footer flipped to `(never synced — run 'imsg sync' to populate the store)`. Same command, same underlying contact set, wildly different output shape depending on what ran before it. This needs a controlled re-test (fresh process, no `--sync` in between) to determine whether `--list`'s output format depends on hidden state left by a prior `--sync` call.
16. **`imsg contacts --sync` reported `synced 0 contacts`, contradicting earlier syncs in this same session that reported `194 contacts synced` with no config change in between.** Possibly legitimate (0 *new/changed* contacts since last sync, if `--sync` is incremental) — but combined with finding 15's format flip immediately afterward, it's not clear the two are unrelated. Not root-caused further.
17. **Real phone-number normalization bug, confirmed via `--raw` comparison.** `imsg contacts --get b8` (one of the odd-format UIDs from finding 15) returned no name and `+4401753866488` — not a valid E.164 number (13 digits after `+`, malformed). `imsg contacts --get b8 --raw` revealed the actual stored value: `+44(0)1753866488`, a normal UK number with the optional trunk-code `(0)` in it. The normalization logic strips punctuation/parens but does **not** correctly drop the `(0)` UK trunk prefix, producing a corrupted number instead of the correct `+441753866488`. This is a genuine bug in phone-number handling, not a display issue — any downstream feature relying on this normalized number (dialing, matching, dedup) would get a wrong number for this contact and likely others with similar trunk-code formatting (common outside the US).
18. **Positive finding — `--lookup` normalizes correctly, unlike `list --from` (finding 2).** `imsg contacts --lookup 4084559969` (bare, no `+1`) and `imsg contacts --lookup +14084559969` both correctly resolved to "ethan" / `+14084559969`. This contrasts with `imsg list --from`, which silently fails on the same bare-number format (finding 2) — confirms the normalization gap is localized to that one command, not systemic across the CLI.

**Findings from `imsg daemon uninstall` testing (2026-07-24):**

19. **`imsg daemon uninstall` reports failure even though it succeeds.** Ran `imsg daemon uninstall` against the `imsg-daemon.service` systemd user unit (confirmed installed/enabled beforehand via `systemctl --user list-unit-files`, unit file present at `~/.config/systemd/user/imsg-daemon.service`). Command exited with code 1 and printed: `Error: uninstalling daemon service` / `Caused by: 0: service operation failed: ... Failed to disable unit: Unit imsg-daemon.service does not exist` (the same error duplicated at levels 0 and 1). But checking actual state immediately after: `systemctl --user list-unit-files` returns nothing for imsg, the unit file is gone from `~/.config/systemd/user/`, and `systemctl --user status imsg-daemon.service` says "could not be found." **The uninstall genuinely worked — the file and registration are gone — but the command reports it as an error.** Likely cause: the uninstall logic removes the unit file first, then calls `systemctl --user disable` on it, which naturally fails ("unit does not exist") because the file it would target is already gone — an ordering bug, not a real failure. This would mislead a script (checking exit code) or a user (reading the error) into thinking uninstall failed when it didn't; the GUI's Settings screen "Daemon controls: ...uninstall against the real service manager" checklist item should watch for this exact false-negative.

Relevant to the checklist's "Splash animation..." and "Device list picker..." items, which currently read as two back-to-back stages rather than overlapped ones.
26. **Default viewport has an unnecessary scrollbar / needs scrolling to fit content that should fit natively.** Some layout/sizing issue causes a scrollbar to appear on the default viewport even when there's no content overflow requiring it, and the user needs to scroll down to see content that should already be in view. Not yet isolated to a specific screen/component.
27. **Serious — GUI reported "Connected" while the phone's Bluetooth was off, and messages never arrived.** *(Root cause corrected 2026-07-27; the original diagnosis in this entry was wrong.)* The GUI's status display is **not** hardcoded: `use-daemon-status.ts` polls `commands.daemonStatus(addr)` every 5s, `daemon_status` (`imsg-gui/src/commands/daemon.rs:47`) delegates to a real `broker_client::query_state`, and `StatusPanel.tsx:31` maps `active` → "Connected". Every link in that chain reports what it is told. The defect is in the **producer**: the broker actor only ever learned a session was dead *mid-op*. `serve_active` (`imsg-broker/src/runtime/actor/serve/mod.rs`) could reach `ServeOutcome::Dropped` from exactly two places — an op handler or an MNS handler returning `OpOutcome::SessionLost` — and both require traffic. A daemon in steady state generates none: status queries are answered from the state watch without touching the device, the GUI's 5s message poll reads the local store, and a dead link produces MNS silence rather than events. Nothing in the tree consulted BlueZ or the socket after connect (`imsg-transport/src/rfcomm.rs` used `peer_addr()` only during the `BT_CONNECTED` gate), so the authoritative state — which BlueZ publishes continuously on D-Bus — had no subscriber. The actor stayed `ConnState::Active` indefinitely and the GUI faithfully rendered a state that was itself stale. A second, narrower hole compounded it: when the MNS stream ended (exactly what link death causes) the `else` arm set `mns_rx = None`, silently disabling notifications and *removing* the one passive detection path that remained. **Status: partially fixed 2026-07-27** — the actor now consumes BlueZ link events and drops the session on `Connected=false` without needing traffic (see `runtime/actor/tests/link.rs`). The MNS-restart half is still open; it needs an injectable MNS listener before it can be driven under test. Finding 14 is a narrow instance of the same missing-liveness gap rather than a separate defect.
