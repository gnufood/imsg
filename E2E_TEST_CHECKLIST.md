# Live end-to-end test checklist

Written 2026-07-23. Companion to `GUI_NEXT.md` §1 ("Live end-to-end test — not yet run — the
one unmet validation"). Everything below is unit/integration tested (real sockets, real
SQLite, hermetic keyring bypass) but never exercised as a running app against a real phone.

This list was built by diffing local `main` against `origin/main` (66 commits ahead, 0
behind — nothing pushed since `686b6c0`) rather than assuming the gap was GUI-only. A
significant share of what's untested is backend/CLI: a new `imsg-broker-client` crate, a CLI
lib/bin split with a rewritten dispatch/broker path, live (non-cached) PBAP contact ops routed
through the broker, RFCOMM `BT_SECURITY` support (`setsockopt`, explicitly noted in-tree as
untested against hardware), real Bluetooth SDP discovery, and a config-layer rewrite
(`toml_edit`-typed writes, `SecurityLevel`). See `GUI_NEXT.md` §1 for setup/run/verify
procedure (config stashing, log locations, screens viewable without a phone).

**Findings from Phase 1 (no daemon, no sync):**
1. `folders` errors instantly on every call — needs separate root-cause pass.
   - **Fix landed 2026-07-28 (`f3f7ba9`, `480d513`); finding stays open — never re-tested against hardware, and the diagnosis below was never confirmed against the live failure.** Code read, not reproduced: `folders` was the only device-touching command that opened its own MAP connection, calling `conn::connect_map` directly while every sibling (`list`/`get`/`threads`/`send`/`delete`/`sync`/`contacts`) went through `broker::call`. There was no `BrokerRequest::Folders` variant, so it *couldn't* share the session. Since `broker::call` auto-spawns a broker via `spawn::ensure_running` and that broker holds the device's single RFCOMM server channel for its idle window (15s default, indefinite under the daemon), any `folders` run in that window was a second connect to an owned DLCI — which fails immediately at the kernel rather than timing out, matching "instant error every invocation". Under the Phase 3/4 daemon it could never have succeeded.
   - Now routed like every other live read: `session::live::folders` → `BrokerRequest::Folders`/`BrokerResponse::Folders(Vec<FolderDto>)` → `DeviceOp::LiveFolders` → `broker_client::folders`. Output also gained the `(live from device)` footer the other live reads carry. 13 unit tests across the five layers (scripted OBEX server driving the real SETPATH/GET sequence off `get_folder_listing_000_rsp.bin`, plus a real-socket fake broker) — all against fakes, so none of them prove the channel contention is gone.
   - **What the re-test must capture, and why it still matters:** run `imsg folders -vv` cold (no daemon, no broker in `ps`, nothing run in the preceding 15s) *and* with the daemon up. If the cold run had been failing for a second, unrelated reason, this change would not have surfaced it — no cold run was ever performed, before or after.
2. `list --from` does no phone-number normalization: `--from 4084559969` (bare, no country code) silently returns `(no messages)` instead of matching or erroring; `--from +14084559969` works correctly. Likely wants normalization or a clearer no-match distinction from a malformed-filter case.
3. `get <handle>` on a message just sent via `send` shows `From:` blank and `Folder: telecom/msg/inbox` — an outbound message reporting as inbox with no sender looks wrong, though semantics of `From` for self-sent messages need confirming against intended design.
4. `get <handle>` does not reflect post-`delete` state: after `imsg delete <handle>` succeeded and the message was confirmed moved into the `deleted` folder (via `imsg list deleted`), `imsg get` on that same handle still showed the original `Folder: telecom/msg/inbox` and `Status: unread` — stale read, not reflecting the actual current folder/status.

**Findings from Phase 2 (no daemon, sync'd):**

5. **`imsg sync` output is misleading, and `threads`/`list` print a false "never synced" footer despite reading real synced data correctly.** `imsg sync` only ever printed a contacts count ("sync complete; 194 contacts synced", then "0 contacts synced" on a second run) with zero indication of message-sync activity, which looked at first like `sync` wasn't backfilling messages at all. Opened the local SQLCipher store directly (`sqlcipher` CLI, key retrieved from the OS Secret Service under service=`imsg`/account=`database-encryption-key` — see `imsg-keyring` crate, `SERVICE`/`ACCOUNT` consts in `crates/imsg-keyring/src/lib.rs`) and confirmed: `messages` table has 10 real rows, `folder_cursors` shows all four folders (`inbox`/`sent`/`deleted`/`outbox`) with `sync_status: complete`, and the row content/order exactly matches what `imsg threads`/`imsg list` display. **So sync genuinely works** — the bug is purely in the CLI's status footer, which prints `(never synced — run 'imsg sync' to populate the store)` unconditionally instead of checking actual sync state (e.g. `folder_cursors.sync_status` or `meta.sync_enabled`, both of which correctly show synced/true in the DB).
6. **Data-loss/mismatch between live and synced views.** Phase 1's live `imsg threads` showed a 5th thread, `4084765919` (1 message, no `+1` prefix), that is completely absent from the synced store — neither in `messages` nor reflected in synced `threads` output. Needs investigation: could be a phone-number-format edge case in the sync ingest path (numbers without a leading `+1` being dropped or mis-keyed), separate from finding 2's CLI-arg-normalization issue but possibly related.
7. **Re-tested via CLI: handle itself is stable; real cause is `send` misfiling into the wrong folder, which then makes `delete`'s default `--folder inbox` target the wrong place.** Sent a fresh throwaway test message (`imsg send +14084559969 "...handle-check..."`) and immediately checked `imsg list outbox -l`, `imsg list sent -l`, `imsg list inbox -l --from +14084559969`. Result: the handle `imsg send` returned (`C2A3F32A1F13411`) matches **exactly** in `imsg list sent -l` — handle is stable, not reassigned between outbox/sent as originally hypothesized. This directly contradicts the earlier hypothesis in this entry (now struck through) and rules it out. However, this new message correctly landed in `sent`, whereas the original Phase-1 test message was sitting in `inbox` (confirmed via the direct DB read in finding 5's investigation). So the real anomaly is that the **Phase-1 send was misfiled into `inbox` instead of `sent`** — and since `imsg delete` defaults to `--folder inbox` when `--folder` is omitted, deleting a message that's actually resting in `sent` while asking for `inbox` would explain the original apparent no-op (issue #4).
   - **CONFIRMED (2026-07-24):** `imsg delete 7B093DFC01064E4` (the original Phase-1 test message handle, no `--folder` flag, so defaulting to `inbox`) succeeded this time — `deleted 7B093DFC01064E4`. This matches the theory: the message really was resting in `inbox` (not `sent`), so the default-folder delete correctly targeted it. **Still open:** why did this message land in `inbox` in the first place when a separately-sent message (`C2A3F32A1F13411`) correctly landed in `sent`? Two `send` calls, same recipient, inconsistent filing folder — root cause not identified, needs a controlled repro (multiple sends in a row, compare filed folder each time).
   - Earlier retries of `imsg delete C2A3F32A1F13411 --folder sent` and later `imsg delete C2A3F32A1F13411` (no folder) both failed with `Error: device unreachable — bring the phone close and check Bluetooth`, while `imsg send`/`imsg list` succeeded moments before and after. Suggests `delete` specifically may be hitting connection issues that `send`/`list`/`threads` don't — could be a distinct RFCOMM/MAP-session problem for the delete op path, not just generic Bluetooth flakiness. Not yet root-caused; only anecdotal from this session's ordering of commands.

8. **CONFIRMED real bug, not resolved by finding 7 — self-sent message missing from `inbox` entirely.** Sent `imsg send 4084559969 'test'` (handle `5415C2A2E386484`) — **`4084559969` is the user's own number**, i.e. this is a self-send. `imsg list sent -l` correctly shows it filed in `sent`. But unlike a normal SMS-to-self (which should arrive back as a received message too, since the phone is messaging itself), it **never appears in `inbox`** across repeated checks and elapsed time. This is a real gap, not just "wrong folder checked" — a self-sent message should reasonably show up in both `sent` and `inbox` (or the CLI/store needs to explicitly document that self-sends are sent-only, if that's intended MAP/carrier behavior — not yet known which).
9. **`[sent?]` status marker — the literal question mark suggests the code itself is uncertain about outgoing status, not just display polish.** Both `5415C2A2E386484` and `C2A3F32A1F13411` show `[sent?]` in `imsg list sent -l` output. This isn't a normal terse status label — the trailing `?` reads as the implementation being unsure whether the message actually reached `sent`/delivered state, likely tied to the `outgoing_status` column seen in the local DB schema (finding 5's investigation: `messages` table has an `outgoing_status` column). Needs clarification: is `[sent?]` a deliberate "unconfirmed" state the CLI surfaces intentionally, or a placeholder/bug where a proper status was never wired up?
10. **`(never synced...)` footer bug (finding 5) also reproduces here** — `imsg list sent -l` still prints `(never synced — run 'imsg sync' to populate the store)` despite this being the same already-synced store confirmed working in finding 5. Same root cause, just noting a second reproduction in a different folder view.

**Findings from Phase 3 (daemon, no sync):**

11. **UPDATE to finding 8 — self-sent messages DO eventually land in `inbox`, just not immediately, and under a NEW handle different from the one `send` returned.** Under Phase 3 (daemon started fresh, no sync), `imsg list -l` (default inbox, live from device) now shows both Phase-2 self-sent test messages present in `inbox`: `D6588BB7B23E462` ("test") and `9616AE14328D4EE` ("imsg e2e test - handle-check..."). Neither handle matches what `send` originally returned for these messages (`5415C2A2E386484` and `C2A3F32A1F13411` respectively) — confirmed via `imsg list sent -l`, which now shows `(no messages)`, i.e. they've moved out of `sent` entirely and into `inbox` under fresh handles. So finding 8 is resolved as "not a bug, just eventual/delayed delivery" — but this surfaces a **new, more significant issue**: a message handle is not stable once a self-sent message completes its round trip from `sent` to `inbox`; anything that cached/referenced the original `send`-returned handle (e.g. a GUI showing "message sent" tied to that handle, or a future `delete`/`get` call using it) would silently be referencing a handle that no longer resolves to the message's current location, without any indication the handle changed.
12. **Not an `imsg` bug — Apple/iOS doesn't honor MAP delete-status requests.** `7B093DFC01064E4` was confirmed deleted in Phase 2 (`imsg delete 7B093DFC01064E4` succeeded, absent from subsequent `list` output within that phase/session) but reappeared unchanged in `inbox` under Phase 3 (fresh daemon, no sync). **User-confirmed root cause: this is known iOS behavior — Apple's MAP server implementation does not durably persist/respect delete-status flags set by an accessory.** `imsg`'s `set_message_status_deleted` call is working as intended (finding 7 already confirmed the CLI correctly applies the delete request when given the right folder); the phone simply doesn't keep it applied. Not actionable on the `imsg` side beyond documenting the limitation — e.g. the GUI's delete-conversation flow (checklist item under "GUI — Messages screen") should probably not present delete as a guaranteed-permanent action against an iPhone, since the device itself can silently un-delete.

**Findings from Phase 4 (daemon, sync'd):**

13. **CONFIRMED real bug — `imsg delete` hard-fails with a local SQLite `FOREIGN KEY constraint failed` when the target message isn't present in the local synced store, even though it exists on the device.** Sent a fresh message under Phase 4 (`imsg send +14084559969 "...phase4 daemon-sync..."`, handle `47BD9811294F46B`). `imsg get 47BD9811294F46B` correctly found it on the device (`Folder: telecom/msg/sent`, body correct). But `imsg list sent -l` does **not** show this message at all (only an older Phase-3 leftover message) — reproduced on retry, not a timing fluke. `imsg list outbox -l` is also empty. Then `imsg delete 47BD9811294F46B --folder sent` fails outright: `Error: operation failed: connection error: Error("FOREIGN KEY constraint failed")` — a raw SQLite error surfaced to the user with `-vv` adding no further context (no table/column named, no indication what local row was expected to exist). Root cause (not confirmed further per staying within CLI-observable behavior): `delete` likely tries to update/insert a row in the local synced store keyed to the message, but since `sync` never actually pulled this particular message into the local `sent` table (matching the `list sent` gap), the FK reference has nothing to point at, and the write fails instead of falling back to a live-only delete path. **This is worse than a cosmetic bug** — a delete request that fails with a raw DB error, on a message that verifiably exists (per `get`), leaves the user with no clear signal of what happened or how to recover (was it deleted or not? does retrying help? should they re-sync first?).

**Deferred check — RUN (2026-07-24).** `imsg daemon stop` immediately followed by a plain `imsg list`, no delay, to check for a lifecycle race between daemon-stop and the CLI's dispatch-path fallback to direct/no-daemon mode.

14. **Confirmed real race, but benign in practice — `imsg daemon stop` is asynchronous, and `imsg daemon status` can report stale `connected` state immediately after.** Sequence: `imsg daemon stop` printed `daemon for EC:0D:51:C7:58:64: stopping` (not a final "stopped" state) → immediately ran `imsg list`, which succeeded cleanly with fresh live data and the correct `(live from device)` footer, no error or hang → immediately ran `imsg daemon status`, which reported **`connected`** (stale — the daemon was actively shutting down, not connected) → waited ~3s and re-checked: `not running`, confirmed by both `imsg daemon status` and an empty `ps aux` grep. **So the actual risk is narrower than originally feared**: `list`/other commands handle the mid-stop window gracefully by falling back to a direct connection rather than erroring or hanging against the dying daemon. The real gap is purely in `daemon status` reporting: for some window after `stop` is issued, `status` can claim `connected` when the daemon is in fact already tearing down. Low severity on its own, but worth fixing since anything polling `daemon status` (including the GUI's `StatusDot`, per the checklist's GUI-Settings section) could show incorrect state for a few seconds during shutdown.

**Findings from `imsg contacts` testing (2026-07-24, daemon running, sync active from Phase 4):**

15. **`imsg contacts --list` returns inconsistent formats/data across consecutive calls.** First call (`imsg contacts --list --limit 10`) returned clean, real data: UIDs like `41.vcf`/`42.vcf`, names like `jason`/`ashton`/`sasha🐺`, footer `(live from device)`. After running `imsg contacts --sync` (which reported `synced 0 contacts` — see finding 16), a second `imsg contacts --list --limit 5` returned **completely different-looking data**: short hex-like UIDs (`b8`, `9f`, `d1`), garbled/wrong "names" (`20 lines`, `6 lines` — these look like leftover vCard line-count artifacts, not names), and the footer flipped to `(never synced — run 'imsg sync' to populate the store)`. Same command, same underlying contact set, wildly different output shape depending on what ran before it. This needs a controlled re-test (fresh process, no `--sync` in between) to determine whether `--list`'s output format depends on hidden state left by a prior `--sync` call.
    - **Partially explained 2026-07-28 (code read, not re-tested).** The format flip is by design, not hidden state. `--sync` sets the `contacts_synced` meta flag, and `commands/dispatch.rs` routes every subsequent `contacts` read to the local store rather than the device once that flag is set. The first call therefore listed live PBAP handles (`41.vcf`) and the second listed cached UIDs — two different key spaces, with the footer following the same fork. Undiscoverable from the output, but working as intended. The `synced 0 contacts` half is finding 16, now fixed.
    - **Still open, and what the controlled re-test should capture:** (a) the `(never synced …)` footer appearing *after* a successful `--sync` — `contacts_synced` and `contacts_synced_at` are written in the same call, so the dispatcher reading one as set while the footer reads the other as absent points at the CLI and the daemon resolving different DB paths; capture the resolved path for both processes and `SELECT key, value FROM meta WHERE key LIKE 'contacts_%'`. (b) The garbled cached names (`20 lines`, `6 lines`) — no such string exists anywhere in the tree, so they are data the sync itself wrote; dump `SELECT uid, display_name FROM contacts` and diff against a live `--list` of the same phonebook. Finding 16's new `no_uid`/`pull_failed` counters make the vCard-ingest side of this readable straight from the CLI now, instead of needing the SQLCipher session finding 5 required.
16. **`imsg contacts --sync` reported `synced 0 contacts`, contradicting earlier syncs in this same session that reported `194 contacts synced` with no config change in between.** Possibly legitimate (0 *new/changed* contacts since last sync, if `--sync` is incremental) — but combined with finding 15's format flip immediately afterward, it's not clear the two are unrelated. Not root-caused further.
    - **Status: fixed 2026-07-28** (`99b421b`, `f3924d1`). The `0` was legitimate; the *reporting* was not. `session::contacts::sync_contacts` returned a bare `usize`, which collapsed two unrelated outcomes into the same value: an unchanged phonebook watermark (early return, nothing fetched) and a refresh that ran and stored nothing. So the 194-then-0 sequence was correct incremental behaviour throughout — the second run matched the device's `DatabaseIdentifier` + version counters and skipped the pull — but the output gave no way to tell that from a failure. It now returns `SyncReport = UpToDate | Refreshed { listed, pull_failed, no_uid, written, wiped }`, carried over the wire as `SyncReportDto` (replacing `ContactsSynced { count }` outright — pre-release, no compatibility variant), and the no-op prints `contacts already up to date`.
    - The same change closed a quieter loss on that path, which this finding didn't catch and the old count could never have shown: `refresh_contacts` skips entries whose vCard pull fails and drops entries carrying no `UID`, both silently, so a phonebook of 400 could report `synced 194 contacts` with 206 discarded. Those are now counted and surfaced — `synced 194 contacts (4 failed to fetch, 2 without a UID)`, and `(cache rebuilt)` when a changed `DatabaseIdentifier` forced a full wipe first.
17. **Real phone-number normalization bug, confirmed via `--raw` comparison.** `imsg contacts --get b8` (one of the odd-format UIDs from finding 15) returned no name and `+4401753866488` — not a valid E.164 number (13 digits after `+`, malformed). `imsg contacts --get b8 --raw` revealed the actual stored value: `+44(0)1753866488`, a normal UK number with the optional trunk-code `(0)` in it. The normalization logic strips punctuation/parens but does **not** correctly drop the `(0)` UK trunk prefix, producing a corrupted number instead of the correct `+441753866488`. This is a genuine bug in phone-number handling, not a display issue — any downstream feature relying on this normalized number (dialing, matching, dedup) would get a wrong number for this contact and likely others with similar trunk-code formatting (common outside the US).
18. **Positive finding — `--lookup` normalizes correctly, unlike `list --from` (finding 2).** `imsg contacts --lookup 4084559969` (bare, no `+1`) and `imsg contacts --lookup +14084559969` both correctly resolved to "ethan" / `+14084559969`. This contrasts with `imsg list --from`, which silently fails on the same bare-number format (finding 2) — confirms the normalization gap is localized to that one command, not systemic across the CLI.

**Findings from `imsg daemon uninstall` testing (2026-07-24):**

19. **`imsg daemon uninstall` reports failure even though it succeeds.** Ran `imsg daemon uninstall` against the `imsg-daemon.service` systemd user unit (confirmed installed/enabled beforehand via `systemctl --user list-unit-files`, unit file present at `~/.config/systemd/user/imsg-daemon.service`). Command exited with code 1 and printed: `Error: uninstalling daemon service` / `Caused by: 0: service operation failed: ... Failed to disable unit: Unit imsg-daemon.service does not exist` (the same error duplicated at levels 0 and 1). But checking actual state immediately after: `systemctl --user list-unit-files` returns nothing for imsg, the unit file is gone from `~/.config/systemd/user/`, and `systemctl --user status imsg-daemon.service` says "could not be found." ~~**The uninstall genuinely worked — the file and registration are gone — but the command reports it as an error.** Likely cause: the uninstall logic removes the unit file first, then calls `systemctl --user disable` on it, which naturally fails ("unit does not exist") because the file it would target is already gone — an ordering bug, not a real failure.~~
    - **Diagnosis above was wrong on both counts; corrected and fixed 2026-07-28.** Reproduced against real systemd rather than inferred. (a) The ordering is the opposite of what was guessed: `service-manager-0.11.0/src/systemd.rs:169-184` runs `systemctl disable` *first*, then `remove_file`. (b) `wrap_output` returns `Err` on any nonzero exit, so when `disable` fails the `?` short-circuits and `remove_file` never runs — the erroring invocation therefore removed nothing. The observed error is exactly what `systemctl --user disable` prints for an already-absent unit (verified: exit 1, same string), so the run that failed was against a unit a *previous* successful uninstall had already removed. Nothing ever "succeeded while reporting failure."
    - **The real defect was a contract mismatch in our own code.** `imsg-service`'s `uninstall` was documented as "a no-op (per the underlying service manager's behavior) if it was never installed" — an unverified claim about a dependency, and false. So `imsg daemon uninstall` exited 1 on a clean machine, breaking unconditional teardown scripts, and the GUI surfaced a raw systemd error for a state the user already wanted.
    - **Status: fixed 2026-07-28.** `uninstall` now queries `status()` first and returns `UninstallOutcome::{NotInstalled, Uninstalled}` instead of `()`, so a no-op is success *and* is distinguishable from a removal — the CLI prints `no daemon service installed (User)` rather than claiming a removal it didn't perform, which would have been the real version of the bug this finding originally described. Absence is detected via the backend's own `status()` (systemd: `systemctl status` exit 4) rather than by matching localized error text. Covered by `crates/imsg-service/tests/real_service_manager.rs`, an `#[ignore]`d round trip against the invoking user's real systemd.
    - **Caveat, deliberately not papered over:** the guarantee is only as strong as each backend's `status()`. systemd and rc.d key off exit codes; `OpenRC` and `winsw` string-match their own output upstream. Verified on systemd only — the sole backend reachable here, since `bluer` makes the whole product Linux-only. Also non-atomic: a service removed between the status check and the removal still surfaces as an error rather than a no-op.

20. **Permissions error on system-service install has no sudo prompt/popup.** Attempting to install the daemon as a *system* service (`--system` flag path, per the GUI's Settings "Daemon controls: ...install(`--system` + per-user)...` item) hits a permissions error with no elevation prompt (no polkit/sudo popup) — the GUI has no path to actually complete a system-wide install interactively; it just fails silently/without a way forward for the user.
    - **Root-caused 2026-07-29 (code read + dependency API verification, not re-tested against hardware).** The failure is four separate things, only one of which is "no sudo prompt". (a) **No elevation mechanism exists anywhere in the tree.** `imsg-service` calls `service-manager` in-process; there is no pkexec, polkit policy, privileged helper, or D-Bus system service. `identity.rs` only *reads* `SUDO_USER`/`SUDO_UID` to decide who the installed unit runs **as** — it never acquires privilege. The design assumes the process is already root (`sudo imsg daemon install --system`); the GUI never is. (b) **The guard that exists doesn't fire for a desktop session**, so the user gets the worst error: `Error::NoInvokingUser` only triggers when the resolved name is empty or root, but in a desktop session `SUDO_USER` is unset and `$USER` is a real user, so the guard passes, `system_identity` returns a valid identity, and the failure lands later at the filesystem write as a raw `Permission denied (os error 13)`. (c) **The affordance was offered with no capability check** — `SERVICES` hardcoded both rows and "Requires root." was description prose. The row looked functional because system-level `systemctl status` is *unprivileged*, so `daemon_service_status(true)` succeeded and rendered a genuine "Not installed" state: reads work, writes don't, and the UI couldn't tell them apart. (d) **The error rendered as muted grey body text**, not an error state — no retry, no guidance — while the neighbouring `serviceStatusPollFailed` gets a real `ErrorState`. That asymmetry is the "no way forward" this finding describes.
    - **Neither dependency offers elevation — verified against rustdoc, not assumed.** Tauri 2.11.5: 318 items in the subtree, full-text search for elevate/privileges/administrator/root returns 0 matches; `tauri::process` contains exactly `current_binary` and `restart`; there is no `Command` in tauri core at all, and `tauri_plugin_shell::process::Command`'s 10 methods (`arg`/`args`/`current_dir`/`env`/`env_clear`/`envs`/`output`/`set_raw_out`/`spawn`/`status`) include no privilege option. `service-manager` 0.11.0: the `ServiceManager` trait has 8 methods, and `set_level` only *selects* system vs. user (which directory to write into) rather than acquiring anything — which is exactly why the failure surfaces at the filesystem write. Note `available()` is **not** a usable capability check: it reports whether the manager exists for the platform, and returns `true` for system-level systemd as an unprivileged user.
    - **Status: GUI affordance removed 2026-07-29; elevation itself deferred.** The GUI no longer offers system install/uninstall. The system row is now **status-only** — the unprivileged status read is deliberately kept, so a system daemon installed from the CLI stays visible rather than becoming invisible to the GUI. The user row's **Install is gated** while a system service is installed (Uninstall is not, so an already-contending install can still be resolved), with an inline reason naming `sudo imsg daemon uninstall --system`. Frontend-only: the three Tauri commands keep their `system` flag, `imsg-gui/src/daemon.rs` keeps `level()`, and `bindings.ts` is unregenerated, so the deferred work is a clean revert away.
    - **Deferred, and the production route is *not* a custom polkit policy.** Polkit doesn't bootstrap itself: a custom action needs a `.policy` file in `/usr/share/polkit-1/actions/` plus a privileged helper, both root-owned, so using it to obtain root requires root first. `pkexec <exe> daemon install --system` is worse than it looks — it authorises *running the binary as root*, and the CLI accepts `--config <path>`, making it a root arbitrary-file-read whose path is then baked into `ExecStart`. The real shape splits placing the unit from controlling it: **packaging** (deb/rpm/AUR) installs the unit as root at package-install time, and the GUI drives `StartUnit`/`StopUnit`/`EnableUnitFiles` over D-Bus to `org.freedesktop.systemd1`, gated by systemd's *existing* `org.freedesktop.systemd1.manage-units` polkit action — a native password dialog with no custom policy, no helper, and no new attack surface. **Prerequisite is distro packaging**, which the current channel can't provide: `dist-workspace.toml` is cargo-dist with `installers = ["shell"]` and `install-path = "CARGO_HOME"`, an unprivileged per-user binary drop with no way to place a policy file or helper.
    - **Separately recorded, because it constrains the whole feature:** a boot-time system service **cannot function before login regardless of elevation**. `imsg-keyring` is Secret Service over D-Bus (`zbus-secret-service-keyring-store`) and holds the DB encryption key; Secret Service is a *session* service unlocked by PAM at login, so a service starting at boot has no keyring to reach and `init_store` fails. The removed row advertised "Runs at boot, independent of login" — a property this architecture cannot deliver. `systemd --user` + `loginctl enable-linger` delivers the achievable half (survives logout) with no elevation at all. Worth settling which of the two is actually wanted before building either.
    - **Still untested / open:** the gate is **UI-only** — `daemon_install` and the CLI have no equivalent check, so nothing prevents a user service being installed alongside a system one programmatically. Not yet exercised against hardware: that the System row reports correct state for a CLI-installed system service, and that the gate engages and the inline reason renders. `--system` install/uninstall from the CLI remains the supported path and is unaffected by this change.
21. **SDP channel-override gate error, same symptom and same workaround as the CLI/setup-picker SDP issue.** Overriding MAP/PBAP channels manually (rather than letting SDP auto-detect from the device) yields the *same* gate error as the original SDP resolution issue that was worked around earlier by repeatedly retrying. ~~Suggests the override path and the auto-detect path may share the same underlying flaky SDP/channel-resolution logic~~, so the override feature doesn't actually route around whatever's unreliable about SDP — it hits the identical failure and needs the identical "just retry" workaround.
    - **Reframed 2026-07-30 (code read + user clarification; not re-tested).** The two paths don't share flaky logic — they are **one function called from two places**. An `sdp:` prefix has exactly one producer in the tree, `transport::discover::resolve_channels`, reachable from the gate picker's Retry and from Settings' **Detect from device**. Both go through `commands.discoverResolveChannels`. The *manual-entry* path (typing numbers, pressing Apply) writes TOML via `config::set_*` and touches no Bluetooth at all, so it cannot emit that string — user confirmed the error says `sdp:` in both cases, which places both observations on the shared function. "The override doesn't route around SDP" is therefore true but trivially so.
    - **The real defect is that nothing retries.** `resolve_channels` is two sequential single-shot `bluesdp::query_rfcomm_channel` calls, each opening its own L2CAP connection, with `?` on the first — no attempts, no backoff, error straight to the UI. The user supplies the retry loop by clicking. By contrast the broker has a full connect policy for the same class of failure (`connect_max_attempts: 3`, `bt_connected_secs: 5`, backoff 500ms→30s, 30s budget). Untouched since `1a584de` (2026-07-15).

Remaining candidates, which compound rather than compete: (a) airtime contention with the daemon's own MAP/PBAP traffic on that ACL, surfacing as `SocketError::Timeout` — `bluesdp` exposes no timeout knob; (b) two independent connects ANDed together, where some devices refuse a second SDP connection immediately after the first closes, making PBAP the systematic loser. ~50% success per attempt is enough to explain "a few clicks and it works" with no exotic cause.
    - **Tracing added 2026-07-30 (`48204e2`) because the path was silent.** `transport/discover.rs`, `imsg-gui/src/discover.rs` and its command were all at zero `tracing::` calls, so `RUST_LOG=debug` produced nothing and no variant was ever captured.     - **The premise is unrecorded.** Nothing anywhere in the repo documents the "original SDP resolution issue" this entry compares against: checklist line 41 marks `imsg config setup` a bare **PASS** with no retry caveat, and greps for flaky/intermittent/worked-around across `internal/*.md`, this file, `CHANGELOG.md` and `ROADMAP.md` return only this finding quoting itself.     - **(a) still open, and it's two defects in one place.** Nothing rejects `map == pbap`: not the form (`use-channel-overrides.ts` checks blank/`NaN` only), not the Tauri commands, not `imsg-config`'s `validate_channel`, which is per-field `[1,30]`. 27. **Serious — GUI reported "Connected" while the phone's Bluetooth was off, and messages never arrived.** *(Root cause corrected 2026-07-27; the original diagnosis in this entry was wrong.)* The GUI's status display is **not** hardcoded: `use-daemon-status.ts` polls `commands.daemonStatus(addr)` every 5s, `daemon_status` (`imsg-gui/src/commands/daemon.rs:47`) delegates to a real `broker_client::query_state`, and `StatusPanel.tsx:31` maps `active` → "Connected". Every link in that chain reports what it is told. The defect is in the **producer**: the broker actor only ever learned a session was dead *mid-op*. `serve_active` (`imsg-broker/src/runtime/actor/serve/mod.rs`) could reach `ServeOutcome::Dropped` from exactly two places — an op handler or an MNS handler returning `OpOutcome::SessionLost` — and both require traffic. A daemon in steady state generates none: status queries are answered from the state watch without touching the device, the GUI's 5s message poll reads the local store, and a dead link produces MNS silence rather than events. Nothing in the tree consulted BlueZ or the socket after connect (`imsg-transport/src/rfcomm.rs` used `peer_addr()` only during the `BT_CONNECTED` gate), so the authoritative state — which BlueZ publishes continuously on D-Bus — had no subscriber. The actor stayed `ConnState::Active` indefinitely and the GUI faithfully rendered a state that was itself stale. **Status: fixed 2026-07-27** — `transport::rfcomm::link_events` subscribes to BlueZ's `Device.Connected` and the actor drops the session on `Down` without needing traffic, on both broker entry points (see `runtime/actor/tests/link.rs`). Finding 14 is a narrow instance of the same missing-liveness gap rather than a separate defect.

    *Correction (same day):* an earlier revision of this entry claimed a second, compounding hole — that the MNS `else` arm swallowed a stream end "exactly what link death causes". **That was wrong.** MNS is a server profile on our side: the phone dials us, `drain_events` returns `true` when one inbound connection ends, and `run_accept_loop` goes straight back to waiting on the still-registered listener. A phone disconnect ends a connection, not the stream, and notifications resume by themselves when the phone returns. `run_mns_session` only returns on a deliberate `stop_mns`, on the actor going away, or on BlueZ ceasing to serve the profile registration (`bluetoothd` restart, D-Bus loss). The `else` arm is therefore an independent, low-severity bug on that rare path — it disables MNS with no recovery for the daemon's remaining life, since the reconnect path deliberately leaves MNS alone and a GUI-only client never subscribes — and was never part of this finding. Tracked separately; the link fix above is the complete fix for the behaviour observed here.

**Findings surfaced while investigating 21 and 22 (2026-07-30, code read only — none reproduced against hardware):**

28. **`security_level` has the identical never-applied gap as the channel overrides, and this checklist asserts behavior that was never built.** `use-security-level.ts` calls `configSetBrokerSecurityLevel` and then `onSaved()` → `reload`, and nothing else — no reconnect, no restart. `security_level` lives in `BrokerConfig`, which the daemon snapshots at spawn exactly like `device.map_channel`, so a running daemon never picks up a change. The GUI-Settings item below claiming "Apply writes and reconnects or fails visibly" describes an expectation, not implemented behavior. This is why finding 22(c)'s fix is being shaped for two consumers rather than baked into the channels card.
29. **`config::set_device_and_channels` is not atomic, despite reading as though it is.** It calls `set_device` → `set_map_channel` → `set_pbap_channel`, each of which runs its own `patch_config` load-edit-write cycle — three separate file writes. Its doc claim ("all three inputs are validated before any I/O, so a rejected channel never leaves a partially-written `address`") is true but narrower than it looks: it covers *validation* failures only. An I/O failure or crash between the calls genuinely can leave the address persisted with stale or missing channels, which is the device-config gate's own write path. Fixing it is ~3 lines once `patch_config` gains a multi-key form, which finding 22(a)'s paired setter needs anyway.
30. **`gate.rs` treats every `config::load` failure as "no device configured".** The gate's loop does `let Ok(cfg) = config::load(...) else { park(AwaitingDeviceConfig) }`, so a malformed TOML file, a failed validation, or an unreadable config is indistinguishable from a first launch — the user is silently dropped into the device picker instead of shown an error. Relevant to 22(a): if the same-channel rule were also enforced at load time, a hand-edited bad pair would send the user to the picker rather than surfacing the reason. That conflation is a latent bug independent of the validation question, and it argues for enforcing the invariant on the write path only until the gate can distinguish the two.
